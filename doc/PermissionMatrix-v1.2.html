1. Roles

Simple role-based auth — a single users.role enum drives every authorization decision. No fine-grained RBAC, no permission table.

3. Soft-Delete Policy

Soft-deletable — lifecycle-bearing:
users, designs, product_templates, product_variants, design_product_mappings, orders, order_items, payments
Hard-delete / cascade — ephemeral:
cart_items, shipments, addresses, profiles, tags, categories, junctions, polymorphic tables

Designer with placed orders cannot be soft-deleted (order_items.design_product_mapping_id is restrictOnDelete). Same for printers with active items.

4. Always-Deny

  • Read another user's email / phone / address — except admin
  • Edit unit_price after order creation — even admin cannot
  • Edit orders.shipping_* after checkout — snapshot immutable
  • Delete design / template / variant referenced by order_items — DB blocks
  • Soft-delete a user with active order_items — application blocks
  • Add cart item to unpublished design or inactive variant — application blocks
  • Bypass cart_items_unique_line via duplicate insert — index blocks

5. Workflow Example · Place & Fulfill an Order

#ActorAction
1CustomerPOST /api/cart/items — mapping X, variant Y, qty 2
2CustomerPOST /api/cart/items — mapping Z, qty 1
3CustomerPOST /api/orders with shipping address → snapshots shipping fields, creates 1 order + 2 items + 1 payment (pending)
4CustomerUploads proof-of-payment via media (collection=payment_proof)
5AdminPATCH /api/payments/{uuid}/confirm
6Printer APATCH …/items/{id}/status → received → printing → printed → handed_off
7Printer APOST /api/shipments — system sets shipped_at, customer notified
8Printer APATCH /api/shipments/{id} → delivered — system sets delivered_at, order derived status = delivered
